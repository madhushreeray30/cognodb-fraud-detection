# Graph Database Schema Documentation

## 🏗️ Schema Overview

This fraud detection system uses a property graph model with three main node types and four relationship types to model financial transactions and detect suspicious patterns.

## 📋 Node Types

### 1. User Node
Represents individual accounts in the system.

**Label**: `User`

**Properties**:
| Property | Type | Description | Example |
|----------|------|-------------|---------|
| `id` | String | Unique user identifier | `U001` |
| `name` | String | Display name | `Alice Johnson` |
| `riskScore` | Float | Risk rating (0.0-1.0) | `0.25` |
| `status` | String | Account status | `VERIFIED`, `SUSPICIOUS`, `FLAGGED`, `HIGH_RISK` |

**Constraints**:
```cypher
CREATE CONSTRAINT user_id IF NOT EXISTS 
FOR (u:User) REQUIRE u.id IS UNIQUE
```

**Use Cases**:
- Track individual account behavior
- Calculate overall risk scores
- Monitor account status changes
- Query user transaction history

### 2. Transaction Node
Represents individual money transfers.

**Label**: `Transaction`

**Properties**:
| Property | Type | Description | Example |
|----------|------|-------------|---------|
| `id` | String | Unique transaction ID | `U001_U002_2026-08-01` |
| `amount` | Integer | Transfer amount in dollars | `5000` |
| `timestamp` | String | Transaction date | `2026-08-01` |
| `flagged` | Boolean | Manually flagged for review | `true` |

**Use Cases**:
- Audit transaction history
- Analyze transaction patterns
- Filter by amount or date
- Track flagged transactions

### 3. Merchant Node
Represents business accounts and payment processors.

**Label**: `Merchant`

**Properties**:
| Property | Type | Description | Example |
|----------|------|-------------|---------|
| `id` | String | Unique merchant identifier | `M001` |
| `name` | String | Business name | `SafeMart` |
| `category` | String | Business category | `RETAIL`, `EXCHANGE`, `SERVICE` |

**Constraints**:
```cypher
CREATE CONSTRAINT merchant_id IF NOT EXISTS 
FOR (m:Merchant) REQUIRE m.id IS UNIQUE
```

**Use Cases**:
- Identify legitimate payment flows
- Track merchant-specific patterns
- Separate P2P from merchant transactions

## 🔗 Relationship Types

### 1. SENT_TO
Direct peer-to-peer transfer from one user to another.

**Direction**: User → User

**Properties**:
| Property | Type | Description | Example |
|----------|------|-------------|---------|
| `amount` | Integer | Transfer amount | `5000` |
| `timestamp` | String | Transaction date | `2026-08-01` |
| `flagged` | Boolean | Suspicious indicator | `false` |

**Constraints**: Amount > 0

**Use Cases**:
- Query direct transactions between users
- Find large transfers (>$10k)
- Identify payment chains
- Detect circular flows

**Example Creation**:
```cypher
MATCH (u1:User {id: 'U001'}), (u2:User {id: 'U002'})
CREATE (u1)-[:SENT_TO {amount: 5000, timestamp: '2026-08-01', flagged: false}]->(u2)
```

### 2. RECEIVED_FROM
Inverse relationship for easier traversal (automatic).

**Direction**: User ← User

**Properties**: Same as SENT_TO

**Generated By**:
```cypher
MATCH (u1)-[s:SENT_TO]->(u2)
CREATE (u2)-[:RECEIVED_FROM {amount: s.amount, timestamp: s.timestamp}]->(u1)
```

**Use Cases**:
- Bidirectional analysis
- Money mule detection (high in-degree)
- Flow analysis from destination

### 3. MADE_TRANSACTION
User initiates a formal transaction record.

**Direction**: User → Transaction

**Properties**: None (time-stamped in Transaction node)

**Use Cases**:
- Query all transactions by a user
- Aggregate user transaction volume
- Calculate user statistics

**Example Creation**:
```cypher
MATCH (u:User {id: 'U001'}), (t:Transaction {id: 'U001_U002_2026-08-01'})
CREATE (u)-[:MADE_TRANSACTION]->(t)
```

### 4. TO_USER
Transaction targets a recipient.

**Direction**: Transaction → User

**Properties**: None

**Use Cases**:
- Query transactions targeting a user
- Analyze incoming transaction patterns
- Find large inflows to high-risk users

## 📊 Query Patterns

### Pattern 1: Circular Transactions (3-hop)
Detect money laundering via circular flows.

```cypher
MATCH cycle = (u1:User)-[t1:SENT_TO]->(u2:User)
           -[t2:SENT_TO]->(u3:User)
           -[t3:SENT_TO]->(u1)
WHERE t1.amount > 5000 
  AND t2.amount > 5000 
  AND t3.amount > 5000
RETURN u1.name, u2.name, u3.name, 
       t1.amount + t2.amount + t3.amount as total_cycled
```

**Graph Advantage**: Single pattern match traverses 3 edges and validates cycle. In SQL, this requires 3 self-joins.

### Pattern 2: Money Mule Detection
Find users with high in-degree and out-degree (many sends and receives).

```cypher
MATCH (u:User)
WITH u,
     size([(u)-[s:SENT_TO]->() | s]) as sent_count,
     size([(u)-[r:RECEIVED_FROM]->() | r]) as received_count
WHERE sent_count > 3 AND received_count > 3
RETURN u.id, u.name, sent_count, received_count,
       (sent_count + received_count) as flow_volume
ORDER BY flow_volume DESC
```

**Graph Advantage**: Degree calculation is O(1) per node. SQL would require GROUP BY and COUNT aggregations.

### Pattern 3: Variable-Length Paths
Find connections between users (up to 5 hops).

```cypher
MATCH path = shortestPath((u1:User {id: 'U001'})-[*..5]-(u2:User {id: 'U105'}))
WHERE u1 <> u2
RETURN [node IN nodes(path) | node.name] as path,
       length(path) - 1 as hops
```

**Graph Advantage**: Variable-length paths are graph-native. SQL requires recursive CTEs or stored procedures.

### Pattern 4: Transaction Hub Analysis
Analyze all incoming and outgoing for a user.

```cypher
MATCH (sender:User)-[sent:SENT_TO]->(hub:User {id: 'U101'})
MATCH (hub)-[outgoing:SENT_TO]->(receiver:User)
RETURN sender.name as source,
       hub.name as hub,
       receiver.name as destination,
       sent.amount as in_amount,
       outgoing.amount as out_amount
ORDER BY in_amount DESC, out_amount DESC
```

**Graph Advantage**: Direct edge traversal without multiple joins.

## 📈 Data Statistics

### Typical Scale (Free Tier Compatible):
- **Users**: 10-1000s
- **Transactions**: 100s-10,000s
- **Relationships**: 1000s-100,000s

### Query Performance Expectations:
| Query Type | Complexity | Time (Free Tier) |
|-----------|-----------|------------------|
| Get single user | O(1) | <10ms |
| List all users | O(n) | ~50ms (100 users) |
| Find user's direct transactions | O(degree) | ~20ms |
| 3-hop cycle detection | O(n²) | ~100ms |
| Variable-length paths | O(degree^hops) | ~50ms (5 hops) |
| Money mule detection | O(n) | ~100ms |

## 🔄 Data Flow

```
1. Create User Nodes
   User("U001", "Alice", risk=0.2)
   └─ Add to graph

2. Create Transaction Edge
   User("U001") -[SENT_TO]-> User("U002")
   ├─ amount: 5000
   ├─ timestamp: "2026-08-01"
   └─ flagged: false

3. Create Explicit Transaction Node (Optional)
   User("U001") -[MADE_TRANSACTION]-> Transaction(...)
   └─ Transaction(...) -[TO_USER]-> User("U002")

4. Create Inverse Relationship
   User("U002") -[RECEIVED_FROM]-> User("U001")
   └─ Auto-created for bidirectional analysis

5. Query Patterns
   Find cycles: Match A-[SENT_TO]->B-[SENT_TO]->C-[SENT_TO]->A
   Find hubs: Count in-degree and out-degree
   Find paths: Variable-length traversal (A-[*..5]-B)
```

## ✅ Validation Rules

### User Node Validation:
```cypher
MATCH (u:User)
WHERE NOT EXISTS(u.id) 
   OR NOT EXISTS(u.name)
   OR u.riskScore < 0 
   OR u.riskScore > 1
RETURN u as invalid_user
```

### Transaction Edge Validation:
```cypher
MATCH ()-[t:SENT_TO]->()
WHERE NOT EXISTS(t.amount)
   OR t.amount <= 0
   OR NOT EXISTS(t.timestamp)
RETURN t as invalid_transaction
```

### Bidirectionality Check:
```cypher
MATCH (u1:User)-[s:SENT_TO]->(u2:User)
WHERE NOT EXISTS((u2)-[:RECEIVED_FROM]->(u1))
RETURN u1.id, u2.id
```

## 🎓 Learning Points

1. **Multiple Relationship Types**: Use different relationship types to model different transaction types
2. **Bidirectional Relationships**: Create inverse relationships for easier querying
3. **Explicit Transaction Nodes**: When transactions need properties beyond amount/timestamp
4. **Variable-Length Paths**: Graph databases excel at finding connections of unknown depth
5. **Aggregation Patterns**: Degree calculations and centrality measures are optimized in graphs
